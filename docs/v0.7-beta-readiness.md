# sndbox v0.7 beta readiness

Reviewed: 2026-08-29

## Supported beta surface

| Component | Beta support |
| --- | --- |
| Desktop application | Windows x64, version `0.7.2-beta.2`, distributed as an explicitly unsigned NSIS installer for invited testing. MSI requires a numeric stable version and is not emitted for this prerelease. |
| Local workflow runtime | Bundled engine, plugin runtime, browser sidecar, SQLite data, OS credential storage, and managed Chromium. |
| Self-hosted runner | Linux x64 and ARM64 archives, an x64 beta OCI image, runner protocol 2, and one concurrent execution on the small-Droplet profile. |
| Public website | `sndbox.app`, served by a standalone Next.js x64 container with release-manifest-backed downloads. |
| macOS/Linux desktop | Not published in this beta. |

The Windows app and Linux runner solve different jobs. The app is the visual editor on a tester's PC. The runner is a headless agent for always-on execution and does not expose the desktop UI over the network.

## UX readiness

- Main app content uses the available desktop width up to a readable 1920 px boundary, with an ultrawide workflow/template split above 2100 px.
- Settings uses a dedicated category rail and centered content at wide resolutions. General, appearance, accessibility, node-editor, connection, browser, and beta preferences are separated instead of accumulating in one card grid.
- Preferences persist locally and immediately drive density, colour, contrast, reduced motion, start view, date display, sidebar width, accessible editing, node descriptions, grid snapping, minimap, hints, and deletion/navigation confirmations.
- Desktop builds check the GitHub release feed on the selected stable or beta channel. A compact dismissible update notice appears only when a newer semantic version is published.

## Release integrity and downloads

The protected tag workflow accepts stable tags and numbered `alpha`, `beta`, or `rc` prereleases. It verifies the package and Tauri versions, permits an explicitly unsigned Windows NSIS installer only for prereleases, builds deterministic Linux runner archives, creates SHA-256 and Sigstore verification material, and emits `release-manifest.json` with a digest and immutable URL for every file. Invite-only prereleases publish x64 containers for the x86_64 beta Droplet without an emulated ARM build; stable releases retain multi-architecture container publication and continue to fail closed without valid Authenticode signing.

The marketing downloads route validates that manifest before displaying live buttons. Until a manifest exists, it links to release status and does not invent an installer URL. Beta tags are published as GitHub prereleases rather than drafts so invited testers can download them.

## Small DigitalOcean deployment

`deploy/digitalocean/compose.yml` runs the standalone website with a 384 MB limit, a 128 MB Caddy TLS proxy, and optionally one runner with a 512 MB limit. The containers are read-only, drop unnecessary Linux capabilities, set `no-new-privileges`, and use bounded PID counts. Runner data, explicitly approved automation folders, and Caddy certificate state are the only writable storage.

Point the `sndbox.app` apex record at the 2 GB RAM / 1 vCPU Droplet; the bundled Caddy service obtains TLS automatically. A reusable, manually dispatchable GitHub Actions workflow uploads the deployment configuration over host-key-verified SSH, pulls an immutable version, waits for container health, and restores the prior website image on failure. Do not expose the runner directly; it makes outbound control-plane connections and publishes no port. Do not place the control plane, PostgreSQL, or browser worker on this beta Droplet.

## Publication gates outside this checkout

1. Configure the `production-release` GitHub environment. Windows signing secrets are optional for prereleases and mandatory for stable tags.
2. Confirm GHCR package visibility for invited testers or provide registry authentication.
3. Push the immutable `v0.7.2-beta.2` tag and approve the protected workflow.
4. Smoke-test the Windows NSIS installer on clean Windows 10 and Windows 11 VMs, verify that its SHA-256 digest matches the release, retain the successful GitHub Actions release record, and confirm the expected unknown-publisher/SmartScreen experience. GitHub artifact attestations remain an additional gate once the repository visibility and account support them.
5. Pair a fresh Linux runner, compare its fingerprint out of band, execute one harmless workflow, and verify drain/restart behaviour.
6. Point the deployed website at the published manifest and test all download links and hashes.

External accessibility review, clean-machine installation evidence, live control-plane credentials, and the release tag cannot be produced from a development checkout and remain explicit beta launch gates. A code-signing identity remains a stable-release gate rather than an invite-only beta gate.
