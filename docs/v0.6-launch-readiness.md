## Homepage message hierarchy

1. Category: local-first visual automation.
2. Outcome: “Automate anything. Run it anywhere.”
3. Scope: browser, files, apps and private network.
4. Differentiation: choose desktop, managed cloud, server, NAS or Raspberry Pi; local runs are not task-metered.
5. Proof: an executable-looking but explicitly non-executing workflow demonstration, browser recorder, node inspector, permission-controlled plugins and governed publication flow.
6. Primary conversion: download; documentation is secondary.

## Design system

The shared palette uses near-black `#08090a`, charcoal surfaces, cool white text and one acid-lime `#d6ff4b` product accent. Radius is held to 4–5 px for controls and product UI. Hairline borders define structure; shadows are reserved for the hero workflow canvas. Display type uses tight system-sans typography, body widths remain narrow, and mono is limited to versions, identifiers and execution values. Motion is confined to the workflow progress demonstration and is removed under `prefers-reduced-motion`.

## SEO audit

- Marketing and docs define canonical metadata bases, unique route titles/descriptions, robots and sitemaps.
- Product, solution and legal paths are finite structured records rather than bulk-generated keyword pages.
- Marketplace pages are server-rendered from reviewed marketplace records; no planned listing is installable.
- Missing: generated social preview image, Article/Product/FAQ JSON-LD, redirects registry and production canonical-domain verification.

## Accessibility audit

Implemented: skip links, semantic landmarks, labelled navigation/search, visible focus, reduced motion, live workflow status, textual demo disclosure, keyboard search, accessible form labels/errors and mobile layouts. Manual screen-reader verification and automated WCAG tooling remain required before publication.

## Performance report

All three applications produce server-rendered or static HTML. Marketing client code is limited to the workflow demonstration, template deep-link fallback, platform detection and contact form. Marketplace reads remain server-side. No third-party scripts, background animation, large images or authenticated application bundle are shipped to marketing visitors. Formal Lighthouse thresholds and CI bundle budgets are not yet configured.

## Release and download pipeline

The current server-runner script builds deterministic Linux x64 and ARM64 tarballs, writes SHA-256 sums and can attach a Sigstore bundle. No public artifact manifest or desktop signed artifact exists. The public downloads UI therefore disables download actions and the account portal does not create substitute URLs. Completion requires a single signed release manifest consumed by the changelog, public downloads and entitlement-aware account API.

## Support workflow

The public support centre routes to documentation, verified downloads, authenticated support and vulnerability disclosure. The account portal does not accept diagnostic uploads because the v0.5 case and guarded-support-access services are missing. When implemented, a case must store approved metadata only, use redacted bundles, issue time-boxed access requests, audit inspection and support early revocation.

## Content authoring

Product and solution content is typed in `@sandbox/content`; docs are typed in `apps/docs/lib/content.ts`. Add only reviewed, version-labelled entries. Legal routes deliberately contain a review gate rather than generated terms. Marketplace content comes from the control plane. Releases must come from the signed release manifest, never a hand-maintained second version list.

## Legal review checklist

- Confirm the legal entity and contact details.
- Reconcile hosted/local data flows with privacy and DPA text.
- Confirm all subprocessors and retention periods.
- Review marketplace, publisher, refund and acceptable-use terms against billing behaviour.
- Confirm vulnerability disclosure safe-harbour language.
- Review regional consumer, cookie and marketing-consent requirements.
- Remove the publication gate only after counsel approval.

## Known limitations

The repository history and services stop at v0.4 despite the stage brief stating v0.5 is complete. Product-plan entitlements, licences, metered usage, signed private releases, support cases, support access, notifications, a validated OpenAPI document, node-reference schema export, analytics, production legal text and deployment configuration are absent. Pricing amounts are intentionally unpublished. macOS/Linux desktop builds and every binary download remain unavailable. The directory depends on a configured live marketplace.

## Migration from v0.5

No v0.5 implementation can be migrated from this checkout. When that branch is supplied: preserve its OIDC issuer and session cookies on `app.sandbox.com`; adapt product entitlements into `@sandbox/api-client`; connect signed release manifests rather than copying versions; wire the existing guarded support provider; generate API documentation from its validated OpenAPI output; and keep desktop workflows untouched.

## Recommended v0.7 scope

After completing the blocked v0.5 and launch gates, focus v0.7 on evidence-backed ecosystem growth: reviewed templates tied to real package versions, publisher quality tooling, richer diagnostics-to-docs linking, regional hosted-runner controls and measured onboarding improvements. Avoid expanding page count until conversion and support journeys have production evidence.
